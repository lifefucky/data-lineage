# Entities lineage — идея и функционал

Локальный операционный граф физических таблиц DWH (Greenplum): увидеть, где пусто и на каком шаге пайплайна оборвался поток данных.

---

## Идея проекта

### Проблема

На цепочке загрузки данных запись может не произойти без явного алерта оркестратора (тихий сбой: задача помечена как успех или пропуск). Диагностика сейчас — точечные SQL и разрозненные отчёты, без единого визуального графа.

### Цель

Дать UI в духе property graph (как Neo4j Browser/Bloom, но локально), где:

- узлы — физические таблицы пайплайна;
- рёбра — поток данных parent → child;
- на узлах видны оценки числа строк и цветовой статус;
- по пути upstream видно, **на каком слое оборвался поток**, а не только факт пустоты.

Это инструмент triage, а не замена журналов ошибок и не lineage «функция пишет витрину» как отдельный продукт.

### Принцип архитектуры

**Топология отдельно, метрики отдельно.**

- Схема графа (узлы + рёбра) пересобирается по явной команде.
- Числа строк кэшируются отдельно и пересчитываются часто (пустые / все) без rebuild графа.

Стек MVP: SQLite + NetworkX + Streamlit/Pyvis. Запись в DWH из Python запрещена — только чтение.

### Итерации продукта

| Итерация | Фокус |
|----------|--------|
| 1 (текущая) | Greenplum: узлы из DDL-экспорта, рёбра по naming / meta / разбору SQL, counts, UI |
| 2 (позже) | Внешний PostgreSQL как upstream к слою загрузки; отдельный тип ребра / слой источника |

### Вне текущего scope

- Служебные/мета-схемы оркестрации как узлы графа
- Экспорт в сторонние аналитические хранилища
- Запись в DWH из приложения
- Обязательная версионная история рёбер и тяжёлый AST/LLM в MVP

## Структура проекта

```text
cli.py                 # build-schema | update-counts | run-ui
models/                # контракты узлов, рёбер, метрик, статусов
builder/               # сборка топологии (скан DDL, рёбра, кэш схемы)
counter/               # live/offline counts, кэш метрик, read-only connector
graph/                 # NetworkX-анализ, цвета статусов
visualizer/            # Streamlit UI + подготовка данных для графа
tools/                 # служебные probe-утилиты (read-only)
lib/                   # vendored JS для графа в браузере
data/                  # runtime-кэши (не в git)
tests/                 # тесты (фикстуры могут быть локальными)
docs/                  # PROJECT.md (в git); остальные черновики локально
```

Поток:

```text
DDL export + meta / SQL bodies
        → builder → кэш топологии
counts (live или mock)
        → counter → кэш метрик
        → graph (статусы, ветки)
        → visualizer (Streamlit / Pyvis)
```

CLI:

| Команда | Назначение |
|---------|------------|
| `build-schema` | Полный rebuild топологии |
| `update-counts` | Обновление чисел строк (без пересборки графа) |
| `run-ui` | Запуск UI |

## Что реализовано

### Топология и рёбра

- Скан узлов из файлового DDL-экспорта (таблицы пайплайна; служебные схемы не в графе)
- Рёбра слоя загрузки по naming
- Рёбра следующих слоёв из meta (offline fixture или live SELECT)
- Индекс источников представлений (view ≠ узел графа)
- Разбор тел функций → рёбра в витрины (с раскрытием view в underlying sources)
- Дедуп meta-рёбер и рёбер из SQL; флаги CLI: урезанный rebuild, отключение SQL-разбора
- Persist топологии в отдельной SQLite; timing в логе CLI

### Counts и статусы

- Быстрый режим (оценки каталога + ladder по партициям) и точный `count(*)`
- Scope: все узлы / только пустые; mock JSON без DWH
- Цвета:
  - **красный** — ноль строк
  - **жёлтый** — аномалия пары parent>0 и child=0 на ранних слоях (приоритет выше красного)
  - **синий** — витрина без входящих рёбер (orphan; после наличия counts)
  - **neutral / unknown** — норма или нет метрик

### UI

- Граф с tooltip и карточкой узла (число строк, режим, время, статус)
- Фильтр по коду источника
- Выбор таблицы → полная ветка (upstream / downstream / both), fallback на окрестность при слишком большой ветке
- Группировка узлов по слоям пайплайна (полосы слева направо)
- Фильтр «слой данных» (зоны пайплайна)
- Фоновый точный пересчёт видимых / пустых с прогрессом и остановкой
- Кэш загрузки топологии в UI по отпечатку файлов БД

### Прочее

- Offline quickstart без VPN/SSH
- Live: одна SSH-сессия на прогон, только SELECT
- Probe-утилита для сверки кэша counts с живым DWH
- Контракты и тесты по ключевым stages (локально)

## Запланированные фичи

Идеи доработок поверх текущего MVP. Детали реализации — в локальных черновиках рядом с этим файлом (не в git).

### UX и triage

1. **Фильтр «только пустые в крайнем правом слое»** — верхняя панель: показать пустые таблицы самой «правой» выбранной зоны пайплайна; держать фильтры источника и слоёв рядом.
2. **Orphan UX** — явная подпись orphan в tooltip/details, caption «сколько orphan видно», легенда (логика цвета уже есть).
3. **Выравнивание status-светофора с кэшем** — при смене топика не показывать ложный red/yellow из устаревших zeros / частичного recount; политика инвалидации и scope пересчёта.
4. **Layout для derived-витрин** — витрины, питающиеся от других витрин, визуально правее «прямо загружаемых» с ядра.

### Качество lineage

5. **Smoke-цепочки** на полном экспорте — каталог типовых паттернов рёбер (ядро → витрина, витрина → витрина) и список gaps.
6. **QA парсера на полном export** — стабильный offline-прогон, отчёт «дыры» (нет refs / неоднозначный target).
7. **LLM только на gaps** — regex first; точечный разбор сложных тел с кэшем ответов, лимитом файлов и без массового обхода всего каталога.

### Продуктовый горизонт (не MVP)

8. Узлы внешнего PostgreSQL (итерация 2)
9. Логи оркестратора / DQ на узлах; сигнал «downstream at risk»
10. Historical сравнение снимков по run/load id
11. Тяжёлый AST-lineage и версионность рёбер
12. Incremental rebuild схемы по mtime отдельных DDL (сейчас только full)

### Ограничения плана

- Python → DWH только SELECT; парсинг тел — по файлам экспорта
- UI ориентирован на subgraph (фильтры / ветка), не на полный граф тысяч узлов сразу
- Meta-рёбра остаются; SQL/LLM дополняют, не обязаны заменять
- Секреты и API-ключи не в репозитории
